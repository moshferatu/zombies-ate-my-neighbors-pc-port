# Analysis toolchain

Phase 1 needs a Code/Data Log, a memory map, and an annotated disassembly. The
plan originally named Mesen2 and DiztinGUIsh for that job. We build the same
artifacts in-tree instead, because:

* **Reproducibility.** A GUI playthrough is not repeatable. `zamn_trace` takes a
  scripted input movie, so any report can be regenerated byte-for-byte, and a
  change in the numbers means a change in the analysis, not a change in how
  someone played.
* **Reuse.** The tracer already *is* most of the Phase 3 co-simulation harness —
  it steps the reference core one instruction at a time with hooked memory
  access. Phase 3 adds a comparison, not a new instrument.
* **It is cheap.** Both tools are a few hundred lines on top of the core that was
  already vendored in Phase 0.

Mesen2 remains useful for interactive spelunking (breakpoints, a live PPU viewer)
and nothing here stops you using it. It is just not on the critical path.

## `zamn_trace`

Steps the vendored SNES core one instruction at a time and records what the CPU
touches. The core is **not modified**: instrumentation swaps the CPU's
read/write handler pointers for wrappers and calls the core's own
`snes_runCpuCycle()`, both of which LakeSnes already exposes.

```
build\zamn_trace.exe "Zombies Ate My Neighbors.sfc" -o analysis -f 2400 ^
    -m movies\level1.zmv --trace-reset 600 --trace-nmi 2000 --png analysis\end.png
```

| Option | Meaning |
| --- | --- |
| `-o, --out <dir>` | output directory (must exist; default `analysis/`) |
| `-f, --frames <n>` | frames to run |
| `-m, --movie <file>` | scripted controller input |
| `--trace-reset <n>` | dump the first *n* instructions after RESET |
| `--trace-nmi <f>` | dump the NMI firing at/after frame *f*, until its `RTI` |
| `--stats-from <f>` | ignore memory accesses before frame *f* |
| `--png <file>` | write the final frame, to check where a movie ended up |

### Outputs

| File | Contents |
| --- | --- |
| `zamn.cdl` | Code/Data Log, one flag byte per ROM byte |
| `cdl_summary.txt` | coverage totals, and a per-bank breakdown |
| `wram_map.csv` | per-address reads, writes, first-touch frame, width, accessor PCs |
| `wram_regions.txt` | the same data collapsed into contiguous live regions |
| `registers.csv` | every `$2000-$5FFF` hardware register access and its callers |
| `subroutines.csv` | every JSR/JSL target, call count, and its callers |
| `callgraph.csv` | caller → callee edges with hit counts |
| `dma_log.csv` | every distinct DMA: source, destination register, length, mode |
| `reset_trace.txt`, `nmi_trace.txt` | instruction traces with loop collapsing |
| `run_summary.txt` | vectors, instruction/NMI/IRQ counts, totals |

### Things worth knowing

* **Loop collapsing.** Traces detect a repeating cycle of up to 16 instructions
  and elide it with a `... N-instruction loop, M further instructions elided`
  marker. Without it a single `MVN` buries everything else.
* **DMA is captured without touching the core.** The write hook sees `$420B`
  (MDMAEN) and snapshots the channel registers *before* the transfer consumes
  them. A-bus→B-bus sources are then marked as data in the CDL, which is how
  graphics get classified without executing them.
* **Fixed-source DMAs are fills, not copies.** A VRAM clear streams the same word
  thousands of times; marking its nominal length as data smeared "data" across
  24 KB of code until this was special-cased. Two such fills exist in ZAMN.
* **Block moves are excluded from the memory map.** The boot `MVN` zeroes all
  128 KB, which would make every byte look live. `MVN`/`MVP` accesses are counted
  in a separate `bulk` column.
* **The APU.** `snes_runFrame()` ends by catching the APU up; that function is
  private to the core, so the tracer instead reads `$2140` through
  `snes_readBBus()`, which performs the same catch-up and has no other effect.

## `zamn_disasm`

Turns a ROM plus its CDL into an annotated 65816 listing. A blind linear
disassembly of a SNES ROM is worthless — code and data interleave, and immediate
operand width depends on the M/X flags. This tool only disassembles bytes the CPU
was *seen* executing, at the widths it executed them with, and dumps the rest as
`.db`.

```
build\zamn_disasm.exe "Zombies Ate My Neighbors.sfc" analysis\zamn.cdl ^
    -b 80 -s tools\symbols\zamn.sym -o analysis\bank_80.asm
```

| Option | Meaning |
| --- | --- |
| `-b, --bank <hex>` | one 32 KB LoROM bank, e.g. `-b 80` |
| `--from`, `--to <hex>` | an explicit SNES address range |
| `-s, --symbols <file>` | extra names; see `tools/symbols/zamn.sym` |
| `-o, --out <file>` | output listing (default stdout) |
| `--code-only` | omit data runs |

Output conventions:

* `sub_BBAAAA:` — a JSR/JSL target. `loc_BBAAAA:` — a jump/branch target.
* Data lines are marked `; read` if the CPU ever read them, `;  ?` if the bytes
  were never touched at all.
* Hardware-register operands are annotated automatically (`STA $2100 ; INIDISP`).
* `; !! M/X width varies here` flags a byte executed at two different register
  widths, where a static disassembly is genuinely ambiguous. ZAMN has 7.

### Addressing convention

The game enables FastROM and immediately does `JML $80:80B6`, so it executes
entirely from the `$80-$BF` mirror. All tools therefore report ROM addresses in
that mirror, which makes listings, traces and the ROM's own `JSL` operands line
up.

## Input movies

Plain text, one state change per line, in ascending frame order. A line's button
set is absolute and stays in effect until the next line.

```
# movies/level1.zmv
0    -
180  Start
188  -
1560 Right
1620 Right+B
```

Buttons: `A B X Y L R Start Select Up Down Left Right`, joined with `+`; `-` or
`.` means nothing held.

Movies are how every report stays reproducible, and they are the same format the
Phase 3 regression harness will replay.

## Regenerating everything

```
powershell -ExecutionPolicy Bypass -File tools\build.ps1
build\zamn_trace.exe "Zombies Ate My Neighbors.sfc" -o analysis -f 2400 -m movies\level1.zmv
build\zamn_disasm.exe "Zombies Ate My Neighbors.sfc" analysis\zamn.cdl -b 80 -s tools\symbols\zamn.sym -o analysis\bank_80.asm
```

`analysis/` is git-ignored: its contents are derived from your ROM and include
verbatim ROM bytes, which this repository does not redistribute.
